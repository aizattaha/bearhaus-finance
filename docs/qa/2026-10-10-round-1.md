# QA round 1 — three independent testers, 10 Oct 2026

**How it was run.** A full local copy of the product (real `app/` and `desktop/` pages, real Postgres schema with every migration, RLS, triggers and RPCs) behind a small Supabase look-alike, so testers could sign up, onboard and use the app exactly as a stranger would — without touching production. Three testers ran in isolation with no knowledge of each other's findings:

| | Persona | Surface | Account |
|---|---|---|---|
| **A** | Mia & Jordan — Melbourne couple, new to budgeting | phone only, AU/AUD | `qa-a-…@test.local` |
| **B** | Wei & Priya — two-country household | phone for capture + Desk for the heavy work, AUD + SGD | `qa-b-…@test.local` |
| **C** | Sam — sceptical solo user | edge cases, data integrity, permissions | `qa-c-…@test.local` |

Raw reports: `report-A.md`, `report-B.md`, `report-C.md` in this folder. 36 bugs were logged in total (14 major, 22 minor); after de-duplication 27 distinct issues remain. Numbers verified against SQL: 31 checks, 27 pass — the four failures are all the same root cause (F1).

**Already fixed before this round closed** (found while building the harness): multi-country sign-up crashed on duplicate starter fund names, and starter cards had no kind/currency (`20261010010000_setup_multicountry`). Not yet deployed to production — it ships with the first fix batch below.

## Common feedback — what two or three testers hit independently

1. **Future-dated ("Scheduled") rows are counted in the Budget tab but nowhere else.** Home, Float, Funds, Desk Pots and the `fund_balances` view all exclude rows dated after today; the Budget tab's "October so far", "still available" and the per-group pace cards include them. Same screen, two answers (A-B3, B-check, C-B4). Home → Recent also lists those rows at the top labelled "today" (A-B5, B-B11, C-B5).
2. **Cash can't be chosen for a named payer.** The card picker filters cards by the payer's profile and Cash belongs to nobody, so "Mia paid cash" is impossible unless the payer is switched to Joint — and the error message then tells you to pick Cash (A-B1, C-B8). A first-day blocker for a new household.
3. **Developer's data leaking into a general product.** Card placeholder "e.g. Amex - Aizat" (A, B); the Desk Pot swap page's defaults and copy hard-code *Investment Fund AU (Aizat)*, *BearHaus Rainy Day AU*, *Future DreamHouse SG*, "Paid with Singapore money" — for any other household the form defaults to Savings → Savings and the Record button is disabled with no reason (B-B4, C-B13).
4. **Money formatting.** Negative balances render as `A$-1,580.50` instead of `−A$1,580.50` (A-B7, B-B6); zero-decimal currencies (IDR, JPY) show two decimals everywhere (A-B9, B-B11); credits/refunds are grey `−` on the phone and green `+` on the Desk (B-B6).
5. **New payment card defaults.** Currency defaults to "multi" even in a one-currency household; the row caption doesn't refresh after changing kind/currency; the Add button is clipped at 390px (A-B8, B, C-B16).
6. **Plan income vs real income double-counts on Home.** Applying a plan books its income lines as fund income; logging the actual salary adds it again, and nothing says so (A, B).
7. **Confirmations.** Browser `confirm()` dialogs on the Desk and 3-second "tap again" confirms on the phone feel foreign / too short (A, B, C).
8. **Desk Statements opens on the most recent *closed* period**, which for a new user (and for calendar-month bank accounts) is empty (B, C).
9. **Locks surprise people.** Cash rows lock themselves on save; a minute later the edit sheet refuses "locked: this row is reconciled — un-reconcile it first" and the words never appeared in the tour (A-B2). Testers B and C found the server-side enforcement itself correct.

## Serious findings from a single tester (must-fix regardless)

Security / integrity (all from C, all verified by direct calls from a signed-in page):

- **C-B1** A login can insert a second `households` row directly (RLS `with check` only tests ownership). The app then fails its `.single()` and silently runs on cached data; every RPC's `select id into v_hh from households where owner_user_id = auth.uid()` becomes ambiguous.
- **C-B2** The reconciliation lock can be bypassed by one UPDATE that sets `reconciled_at = null` *and* changes the amount — the lock triggers only test "was reconciled AND still reconciled".
- **C-B3** One half of a transfer can be deleted at the DB level (auto-reconciled rows aren't protected), leaving an orphan that inflates the other fund.
- **C-B7** A row can reference another household's profile, fund, card or trip (plain FKs, no household check). Invisible through RLS, but it pollutes the other household in any service-role/export query.
- **C-B6** A corrupted session token renders a *zeroed* Home (plan not set up, A$0 everywhere) instead of the sign-in screen — looks like data loss.
- **C-B14** `check_invite` is an unthrottled true/false oracle callable by `anon`.

Everything else C threw at RLS and the RPCs held: 0 rows or 403 on every cross-household read/write, XSS/SQL strings escaped, double-tap writes one row.

Desk (B): **a closed statement still accepts ticks and Reconcile** (B-B2); bulk edit "(no card)" always fails with a raw NOT NULL error (B-B3); "Un-reconcile selected" ignores the selection and un-reconciles the whole statement (B-B5); the ticked-row count excludes foreign-currency rows so it disagrees with the locks on screen (B-B7); `?rows=nocard` lands on the wrong page (B-B9).

Two-country households (B-B1): no SGD spending pot, no SGD card, no SGD budget rows by default — the second country is half set up until the user discovers Settings → Funds → spending pots.

Phone (A): Funds tab is stale after editing/deleting an expense until reload (A-B4); Home isn't re-rendered after "Apply plan" (A-B6).

## What worked well (all three)

Onboarding validation copy; the plan editor's live equation and apply; calculator keypad; trip sheet currency handling and settle-up; closing-day period maths including day 31 and February; statement import matching (4/5 on a PDF-style paste, CSV with Debit/Credit); bulk-edit lock semantics; pot-swap transfer groups, rate edit, undo and settle-up skip; Pots Spent/Cleared/Pending tying to the cent; RLS scoping; lock error messages; rename of person/fund/group following into history.

## Proposed fix list — for review before building

**Status (11 Oct 2026):** all four batches shipped — batch 1 (`20261011000000_batch1_integrity`), batch 2 (app + desk), batch 3 (app + desk), batch 4 (`20261011010000_batch4_guardrails`). F30 was covered by batch 1's session guard. Open by design: the three items under "Not changing".

Grouped by batch; each item names the layer. "Who" = who reported it.

| # | Fix | Who |
|---|---|---|

### Not changing (by design, flagged so it's a decision not an omission)
- Category and comments stay editable on locked rows (all three testers noted it as sensible).
- A daily expense has no per-row split — "Us"/joint is the shared bucket (A asked; it's the current model).
- Refund = category "Payment" for now; a proper credit flag (B's suggestion) is a design choice to make later.
