## Hard rules
1. **Private data.** The repo is PUBLIC, and GitHub Pages serves every file in it. Never commit real balances, statement figures, invite codes, emails, dumps, or anything from the production database. Fund/card *names* already appear in code and tests and are fine. QA raw reports that quote real numbers go to Drive, not here. `tools/ci/private-data-guard.sh` enforces this in CI. **Real-household data fixes are never migrations**: see `supabase/data-fixes/README.md`. Database error messages carry counts and ids, never amounts, because CI logs are public.
2. **Supabase only.** No other backend, no build step, no framework. Two static pages (`app/index.html` phone, `desktop/index.html` Desk) + `app/common.js`, deployed by GitHub Pages from `main`.
3. **No copy-paste deploys.** Claude commits and pushes to `main`. Migrations under `supabase/migrations/` auto-deploy via `.github/workflows/deploy-db.yml` — *only after* the `test` job applies the whole chain from scratch and `tools/sql-tests/` pass. Never ask Aizat to paste SQL into the Supabase editor.
4. **Every sprint ends with the hygiene step** (Aizat's standing instruction, 14 Oct 2026): SQL tests extended → CI green locally (`tools/sql-tests/run.sh` against Postgres 17 *and* the local Supabase stack, `tools/dev/README.md`) → private-data guard + JS check → browser verification on the local stack with synthetic data → commit/push → confirm the Actions (Checks + both deploy jobs) → handbook section → Drive mirror → short report.
5. **Money invariants are asserted, not assumed.** A move/undo RPC that could change a fund's balance asserts before/after and refuses otherwise. Keep that pattern.
6. Don't add a framework, bundler, or TypeScript. Don't rename the compat views (`daily_expenses`, `travel_expenses`, `fund_transactions`) — both apps and every RPC read them by name.
7. **Every migration states its own grants** (v2 sprint 1). Nothing new is executable or readable by the API roles by default: a new function needs `grant execute … to authenticated` (never `anon` — only `check_invite`/`invite_info` are public), a new table or view needs explicit `grant select/insert/…` plus RLS policies. `tools/sql-tests/test_privileges.sql` checks the catalog and the list of RPCs/tables the apps use — extend it when the apps start using a new one.

## Database conventions (read before touching SQL)
- Two ledgers by meaning: **`expenses`** = every purchase/refund (category, card, payer, optional `fund_id`); **`fund_transactions_all`** = movements and allocations (`kind` movement | allocation | card_payment). `fund_transactions` is a *view* over `_all` hiding soft-deleted rows. Compat views `daily_expenses` / `travel_expenses` split `expenses` by `trip_id`.
- RLS reads `household_members`: `bh_member_of()` (read), `bh_writer_of()` (write: owner|member). Write RPCs resolve the household with `bh_current_household()` and raise `42501 'no household — or your login is view-only'` for viewers. Security-definer RPCs set `set_config('bh.via_rpc','on',true)` so guard triggers can tell an RPC from a raw client write. Newer guards use `current_user in ('authenticated','anon')` = a direct client write (inside a definer function `current_user` is the owner): `b0_expenses_client_guard` / `b0_fund_client_guard` clear server-owned columns on client inserts and freeze grouped fund rows (transfer sides, card-payment legs) against one-sided edits.
- Trigger order on `expenses` is alphabetical by name and matters: `b0_expenses_client_guard` → `bx_expenses_category` (name↔id sync) → `bz_expenses_fund` (fund guard) → `expenses_before_write` → `expenses_card_usable` (archived card refused unless a Desk RPC set `bh.allow_archived`) → `expenses_check_refs` → `expenses_lock` (reconciliation lock: amount/date/currency/card/payer/is_refund frozen; `fund_id`, category, comments free) → `expenses_soft_delete` → `zx_…_by` → `zy_expenses_stamp_pot` (`pot_fund_id = coalesce(fund_id, expense_pot_for(...))`) → `zz_…_touch` → `zza_…_splits` (derived, clients read-only) → `zzz_…_audit`.
- Views that define the money: **`fund_money`** (since sprint 3 the one rule for every fund number, computed in one pass; `fund_balances` (Available), `fund_balances_cleared` and `fund_cash` are thin views over it — change the rule there, once), `fund_cash` (in the bank, owed on cards; includes `card_openings` the fund backs, rows charged to a card, and the card share of trip sends via `expenses.settlement_tx_id`), `card_balances` (opening + charges − credits − payments, all from `pot_start`; a purchase in another currency counts at `settled_amount` or waits as `unsettled`), `statement_balances` (`scheduled` = payments dated after today), `pot_month_spend`. Refunds: positive amount, counted negative everywhere.
- **"Today" is the household's**, never the server's: `(now() at time zone h.timezone)::date` in views, `bh_today(hh)` in functions. `CURRENT_DATE` is UTC on production.
- **The server writes the internal rows**: transfers through `record_transfer` (a deferred constraint trigger refuses, at commit, any change that leaves a transfer or card-payment group unbalanced — sprint 3; a group already broken can only be deleted as a unit), the month plan through `apply_month_plan` (once per month: `plan_applications`; `plan_status` answers applied/saved/version), card payments through `record_card_payment`. Apps may insert fund rows only with kind `movement` (or none — then the remark rule decides) and never `origin = 'planned'`. `fund_transactions_all.kind` has no default.
- Past months stay put: fund/budget-line changes re-file from the household's current month only; a pot with past purchases can't be untagged; a fund with money can't change currency; `pot_start` is set once; `categories.role = 'settle_up'` (Payment) can't be renamed, hidden or deleted.
- Text columns (`category`, `category_group`, `paid_with`) are display copies kept in sync both ways by triggers; ids (`category_id`, `group_id`, `payment_method_id`) are the truth.
- When you add a column the apps need, append it to the compat views too (they are `security_invoker` and rebuilt in the latest migration that touched them).
- **The apps read through read models** (sprint 3): launch = `app_bootstrap()` + `home_summary()`; Budget = `budget_summary(month, currency, months)`; Funds tab and Desk Pots = `household_money()`; Travel = `trip_summary()` + one trip's lines when opened. Any new total shown to a person is computed in SQL and tested there; the browser formats. They read with the caller's rights and the household's today.
- **No probes.** The column/function probes and their fallbacks were removed in sprint 3. Instead, **deploy the database first**: push the migration, wait for both deploy jobs, then push the app change that uses it. Only if the two truly must land together, add a probe for that one column, list it in DECISIONS with a removal sprint, and match only the "not found" codes (`42703`, `PGRST202`).
- **Ids, not names.** Apps send `category_id` and `payment_method_id` (inserts, `save_expense`, `desk_add_expense`, bulk edits); the triggers fill in the name copies. Changing a card by name still works for old clients and moves the card id too.
- **Policies** use `household_id = any (array(select bh_member_of()))` (or `bh_writer_of()`), so the household becomes an index condition; list queries also name the household (`.eq('household_id', …)`) so the newest rows come straight from an index.
- **Derived columns are not edits**: `bh_derived_only()` lists the name copies and stamps per table; a change to only those writes no Activity line and keeps `updated_at`/`updated_by`. Re-filing is `restamp_pots(hh, from, to, currency)`, set-based, and runs only for spending pots / budget lines that name a pot.

## Client rules (v2 sprint 3)
- **Device memory is per login.** Use `store.get/set/remove/json(name)` (keys `bh:<user id>:<name>`), never raw `localStorage` for anything tied to a household or a person; nothing is read before `store.use(uid)` (done in `boot`). Only `DEVICE_KEYS` (the sign-up code, the keyboard height) are global.
- **One way out.** Every sign-out, expired/revoked login, `SIGNED_OUT` event and 401 from the read models ends in `endSession(note)`; removed household access calls `store.clear()`. Don't add a second sign-out path.
- **CSP.** Both pages carry the same Content Security Policy meta tag; a new outside host must be added to both. `'unsafe-inline'` goes when the inline `onclick=` handlers do. No CDN scripts — vendor them with an `integrity` hash.
