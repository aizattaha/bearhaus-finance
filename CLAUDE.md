## Hard rules
1. **Private data.** The repo is PUBLIC, and GitHub Pages serves every file in it. Never commit real balances, statement figures, invite codes, emails, dumps, or anything from the production database. Fund/card *names* already appear in code and tests and are fine. QA raw reports that quote real numbers go to Drive, not here. `tools/ci/private-data-guard.sh` enforces this in CI. **Real-household data fixes are never migrations**: see `supabase/data-fixes/README.md`. Database error messages carry counts and ids, never amounts, because CI logs are public.
2. **Supabase only.** No other backend, no build step, no framework. Two static pages (`app/index.html` phone, `desktop/index.html` Desk) + `app/common.js`, deployed by GitHub Pages from `main`.
3. **No copy-paste deploys.** Claude commits and pushes to `main`. Migrations under `supabase/migrations/` auto-deploy via `.github/workflows/deploy-db.yml` — *only after* the `test` job applies the whole chain from scratch and `tools/sql-tests/` pass. Never ask Aizat to paste SQL into the Supabase editor.
4. **Every sprint ends with the hygiene step** (Aizat's standing instruction, 14 Oct 2026): SQL tests extended → CI green locally (`tools/sql-tests/run.sh` against Postgres 17 *and* the local Supabase stack, `tools/dev/README.md`) → private-data guard + JS check → browser verification on the local stack with synthetic data → commit/push → confirm the Actions (Checks + both deploy jobs) → handbook section → Drive mirror → short report.
5. **Money invariants are asserted, not assumed.** A move/undo RPC that could change a fund's balance asserts before/after and refuses otherwise. Keep that pattern.
6. Don't add a framework, bundler, or TypeScript. Don't rename the compat views (`daily_expenses`, `travel_expenses`, `fund_transactions`) — both apps and every RPC read them by name.
7. **Every migration states its own grants** (v2 sprint 1). Nothing new is executable or readable by the API roles by default: a new function needs `grant execute … to authenticated` (never `anon` — only `check_invite`/`invite_info` are public), a new table or view needs explicit `grant select/insert/…` plus RLS policies. `tools/sql-tests/test_privileges.sql` checks the catalog and the list of RPCs/tables the apps use — extend it when the apps start using a new one. The nightly check's login `bh_monitor` runs exactly `bh_money_check_run` and `bh_backup_done` and reads nothing — never grant it more (`test_safety_net.sql` checks).

## Database conventions (read before touching SQL)
- Two ledgers by meaning: **`expenses`** = every purchase/refund (category, card, payer, optional `fund_id`); **`fund_transactions_all`** = movements and allocations (`kind` movement | allocation | card_payment). `fund_transactions` is a *view* over `_all` hiding soft-deleted rows. Compat views `daily_expenses` / `travel_expenses` split `expenses` by `trip_id`.
- RLS reads `household_members`: `bh_member_of()` (read), `bh_writer_of()` (write: owner|member). Write RPCs resolve the household with `bh_current_household()` and raise `42501 'no household — or your login is view-only'` for viewers. Security-definer RPCs set `set_config('bh.via_rpc','on',true)` so guard triggers can tell an RPC from a raw client write. Newer guards use `current_user in ('authenticated','anon')` = a direct client write (inside a definer function `current_user` is the owner): `b0_expenses_client_guard` / `b0_fund_client_guard` clear server-owned columns on client inserts and freeze grouped fund rows (transfer sides, card-payment legs) against one-sided edits.
- The app login has **no DELETE** on `expenses` / `fund_transactions_all` / their views (E36): rows leave through the bin (`soft_delete_rows`) or a definer RPC; the sent lock fires on DELETE too. RPCs that create rows take a `p_id` so a retap is "already saved" (`record_transfer`, `record_card_payment`, `refund_purchases`); a card with history keeps its type and currency (`bh_card_guard`).
- Trigger order on `expenses` is alphabetical by name and matters: `b0_expenses_client_guard` → `bw_expenses_refund` (a linked refund takes its purchase's category, fund, trip and counting date; every row's `counts_on` is set here) → `bx_expenses_category` (name↔id sync) → `bz_expenses_fund` (fund guard) → `expenses_before_write` → `expenses_card_usable` (archived card refused unless a Desk RPC set `bh.allow_archived`) → `expenses_check_refs` → `expenses_lock` (reconciliation lock: amount/date/currency/card/payer/is_refund frozen; `fund_id`, category, comments free) → `expenses_sent_lock` (a purchase sent to a travel fund keeps amount/currency/card/refund/trip/bin state/settled amount until its send is undone; `bh.via_rpc` passes) → `expenses_soft_delete` → `zx_…_by` → `zy_expenses_stamp_pot` (`pot_fund_id = coalesce(fund_id, expense_pot_for(...))`) → `zz_…_touch` → `zza_…_splits` (derived, clients read-only) → `zzb_expenses_refunds` (after: a purchase's `refunded` total and its limit; refunds re-follow a changed purchase) → `zzz_…_audit`.
- **Cards and funds agree on what is owed** (E36): a card counts from `pot_start` (before it: its opening); so does a fund's Owed on cards — a pre-start card row is cash spent, a pre-start card payment counts nowhere. `bh_owed_gaps()` = card owed − fund owed − the one-sided lines, per household and currency, must be 0 (nightly fail). Change either side's rule and both tests and the nightly check tell you.
- Views that define the money: **`fund_money`** (since sprint 3 the one rule for every fund number, computed in one pass; `fund_balances` (Available), `fund_balances_cleared` and `fund_cash` are thin views over it — change the rule there, once), `fund_cash` (in the bank, owed on cards; includes `card_openings` the fund backs, rows charged to a card, and the card share of trip sends: what their card purchases took, `expenses.sent_amount`, when the card is in the fund's currency), `card_balances` (opening + charges − credits − payments, all from `pot_start`; a purchase in another currency counts at `settled_amount` or waits as `unsettled`), `statement_balances` (`scheduled` = payments dated after today), `pot_month_spend`. Refunds: positive amount, counted negative everywhere.
- **"Today" is the household's**, never the server's: `(now() at time zone h.timezone)::date` in views, `bh_today(hh)` in functions. `CURRENT_DATE` is UTC on production.
- **The server writes the internal rows**: transfers through `record_transfer` (a deferred constraint trigger refuses, at commit, any change that leaves a transfer or card-payment group unbalanced — sprint 3; a group already broken can only be deleted as a unit), the month plan through `apply_month_plan` (once per month: `plan_applications`; `plan_status` answers applied/saved/version), card payments through `record_card_payment`. Apps may insert fund rows only with kind `movement` (or none — then the remark rule decides) and never `origin = 'planned'`. `fund_transactions_all.kind` has no default.
- **Refunds** (DECISIONS E35): a refund against a purchase is a row with `refund_of`, made only by `refund_purchases` (via card = the card it was paid with; via cash = into its fund, the card still owes). The purchase keeps its amount; `refunded` is derived. **Money sums count by `expenses.counts_on`, not `date`** (equal except for a linked refund, which counts on its purchase's day) — use `counts_on` in any new budget or fund sum; cards and statements use `date`. A bulk insert with triggers off must fill `counts_on` itself.
- **Trips** (DECISIONS E33): a travel fund per currency (`funds.pays_trips`; `households.travel_fund_id` is the main one, where spending in a currency with no travel fund is converted; `bh_trip_fund(hh, cur)`, Settings → `set_trip_fund`). One rule, `bh_trip_lines`: a credit-card purchase settles into the travel fund in the CARD's currency at what the card charged (`settled_amount` when the currencies differ — it waits until typed); anything else by the currency spent. A send = a fund row with `trip_id`, one per fund, written only by `send_trip`; each purchase keeps what it took (`sent_amount`), and a send always equals its purchases (nightly check). `undo_trip_send` (or binning the send) takes it back; a send never comes back from the bin. `set_settled_amount` on a sent purchase moves its send with it (`bh_send_resum`, asserted). `bh_rederive_trip_sends(hh)` re-derives every send from the stored facts — server-only, idempotent; run it again when the rule changes.
- **Standard across time** (Aizat, 17 Oct, DECISIONS E32): every row follows today's rules whatever its date — no grandfathered exceptions. When you fix a rule, re-derive history from the stored facts in a deliberate rule-based step (before/after on a restored copy, reviewed with Aizat); keep anything a rule computes recomputable for all time. Aizat is checking every past transaction against his accounts, so changing past rows is expected.
- Past months stay put: fund/budget-line changes re-file from the household's current month only; (this guards everyday edits from re-filing history by accident; a rule fix re-derives on purpose — E32) a pot with past purchases can't be untagged; a fund with money can't change currency; `pot_start` is set once; `categories.role = 'settle_up'` (Payment) can't be renamed, hidden or deleted.
- Text columns (`category`, `category_group`, `paid_with`) are display copies kept in sync both ways by triggers; ids (`category_id`, `group_id`, `payment_method_id`) are the truth.
- When you add a column the apps need, append it to the compat views too (they are `security_invoker` and rebuilt in the latest migration that touched them).
- **The apps read through read models** (sprint 3): launch = `app_bootstrap()` + `home_summary()`; Budget = `budget_summary(month, currency, months)`; Funds tab and Desk Pots = `household_money()`; Travel = `trip_summary()` + one trip's lines and `trip_send_plan(trip)` when opened. Desk Transactions = `ledger_page(...)` over the view `money_lines` (both ledgers, one row shape, `event_key` ties a transfer / card payment / pot swap / month's plan together) — a new kind of fund row needs its `kind` there. Any new total shown to a person is computed in SQL and tested there; the browser formats. They read with the caller's rights and the household's today.
- **No probes.** The column/function probes and their fallbacks were removed in sprint 3. Instead, **deploy the database first**: push the migration, wait for both deploy jobs, then push the app change that uses it. Only if the two truly must land together, add a probe for that one column, list it in DECISIONS with a removal sprint, and match only the "not found" codes (`42703`, `PGRST202`).
- **Ids, not names.** Apps send `category_id` and `payment_method_id` (inserts, `save_expense`, `desk_add_expense`, bulk edits); the triggers fill in the name copies. Changing a card by name still works for old clients and moves the card id too.
- **Policies** use `household_id = any (array(select bh_member_of()))` (or `bh_writer_of()`), so the household becomes an index condition; list queries also name the household (`.eq('household_id', …)`) so the newest rows come straight from an index.
- **Derived columns are not edits**: `bh_derived_only()` lists the name copies and stamps per table; a change to only those writes no Activity line and keeps `updated_at`/`updated_by`. Re-filing is `restamp_pots(hh, from, to, currency)`, set-based, and runs only for spending pots / budget lines that name a pot.

## Client rules (v2 sprint 3)
- **Device memory is per login.** Use `store.get/set/remove/json(name)` (keys `bh:<user id>:<name>`), never raw `localStorage` for anything tied to a household or a person; nothing is read before `store.use(uid)` (done in `boot`). Only `DEVICE_KEYS` (the sign-up code, the keyboard height) are global.
- **One way out.** Every sign-out, expired/revoked login, `SIGNED_OUT` event and 401 from the read models ends in `endSession(note)`; removed household access calls `store.clear()`. Don't add a second sign-out path.
- **CSP.** Both pages carry the same Content Security Policy meta tag; a new outside host must be added to both. `'unsafe-inline'` goes when the inline `onclick=` handlers do. No CDN scripts — vendor them with an `integrity` hash. `frame-src 'self'` lets the Desk frame the phone's add form; `common.js` blanks the page if any other site frames it.
- **One Settings, two layouts** (E38). The Desk's Settings page is the phone's own Settings screen in its desk layout (`app/?embed=settings&layout=desk`: the section list on the left, the open section on the right — `openDeskSection`; phone-only rows hidden). Same functions, same saves: add or change a setting in `app/index.html` only; a desk-only look is CSS under `html.embed-desk`, never a second copy on the Desk. **Every Settings list uses `setList(box, 'Add …', form)`**: a long "＋ Add …" button on top that opens the list's form, the live rows (`setRow` — icon · name · caption · tags · ✎, then the row's buttons), and `.archived('Archived …', items, render)` folding archived ones at the bottom. Row details sit behind a ⋯ (`detailToggle`); reorder with `moveRow` (renumbers `sort_order`).
- **Dashboard** (the Desk's first page): numbers from `fund_history` (each fund at each month-end — `fund_money_asof`, the same rule as `fund_money`), `household_money` and `budget_summary`; net worth = Σ Available per country, the total converted at today's ECB rate. Charts are hand-drawn SVG: two validated colours (#1F63B8 blue, #eb6834 orange — run the dataviz validator before adding a third), SVG attributes take hex, not CSS variables.
- **Trips, one screen, two layouts** (E43). The Desk's Trips page is the phone's Travel screen (`app/?embed=travel&layout=desk[&trip=…]`): change trips in `app/index.html` only; on the Desk a line's edit and "＋ add to this trip" go to the Desk's add panel by `postMessage` (`edit` / `add`). What the card charged is typed on the trip line (`set_settled_amount`; which lines from `bh_trip_lines`), and still on the Desk's statement.
- **One add form, two layouts** (E38). The Desk's "＋ add transaction" (and a row's edit) opens the phone's own Quick Add / edit sheet in its desk layout (`app/?embed=add&layout=desk&mode=…&card=…&date=…`: fields on the left, the dock — keypad, pickers, calendar — fixed in a column on the right and never emptied by typing; `DESK_LAYOUT`); the form answers `ready` / `saved` / `close` by `postMessage` (same origin only). Change adding in `app/index.html` only — never build a second form on the Desk. An archived card passed by the Desk saves through `desk_add_expense` inside the form. A computer keyboard types the amount (Enter after the description, Enter saves).
- **The owner's setup list** (E42): `setup_todo()` (SQL, from the data) + `SETUP_TEXT` (common.js) on the phone's Home and the Desk Dashboard. A feature that gives the owner a job adds an item there — never a HANDOVER line. A fund's numbers explain themselves through `fund_explain()` (same rules as `fund_money`; change both together — `test_ready_for_paige` asserts they agree) and `money_checks()` ("checked to" per card and fund).
- **Joining** (E42): the local stack confirms email and needs 12-character passwords, as production. Test a sign-up there with Mailpit (`supabase status` → MAILPIT_URL). The invite code travels in the account (`user_metadata.invite`); don't rely on device storage across the confirm link (iOS opens Safari).
- **Tours.** Phone: `TUT_STEPS` (stops flagged `isNew` make up "What's new"; bump `TUT_VERSION` when you add or change stops — people who took the last tour get "What's new" once). Desk: `DESK_TOUR`, first visit per login, replayable from the menu. Add a stop when you add a screen or change how one works.
